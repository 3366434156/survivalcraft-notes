## 一句话定位

配方匹配是一个**纯字符串比对器**：工作台/熔炉把网格物品编码成 9 个 `craftingId:data` 字符串，`CraftingRecipesManager.FindMatchingRecipe` 先问各 Block 的 ad-hoc 动态配方、再线性扫静态表，`MatchRecipe` 用**镜像+平移穷举**（无旋转）对齐 3×3 残阵，`CompareIngredients` 只比 craftingId 字符串与 data 整数——"任意原木"就是 5 个方块共用同一 craftingId，"任意颜色"就是配方不写 `:data`。熔炉没有独立配方类，烧的就是 `RequiredHeatLevel>0` 的 CraftingRecipe，走**同一个匹配器**。

## 1 Recipe 数据结构（Survivalcraft/Game/CraftingRecipe.cs:2-27）

| 字段 | 语义 | 备注 |
|---|---|---|
| `Ingredients: string[9]` | 3×3 配料阵，行优先；null=空格 | 元素格式 `craftingId` 或 `craftingId:data`，见 §3 |
| `ResultValue / ResultCount` | 产物方块值 / 单次产量 | 值由 `DecodeResult` 生成（:178-197） |
| `RemainsValue / RemainsCount` | 余渣（容器返还）方块值/数量 | 可选，缺省 0（管理器 :96-100） |
| `RequiredHeatLevel` | 需要的热量档 | 工作台恒传 0；**>0 即熔炉配方** |
| `RequiredPlayerLevel` | 需要玩家等级 | 缺省 1（管理器 :102）；受 `EnableLevelRestrictions` 开关（:16） |
| `Description / Message` | 书面描述 / 命中时弹的小消息 | 支持 `[key]` 本地化（:89-93、ComponentCraftingTable.cs:176-179） |
| `DisplayOrder` | 显示顺序，越小越靠前 | 仅影响排序与配方书展示，**不影响匹配胜负**（见 §2.4） |
| `MaxSize=3` | 阵面常量上限 | 网格可小于 3（玩家背包 2×2），不可大于 3 |

## 2 匹配算法逐段（Survivalcraft/Managers/CraftingRecipesManager.cs，本日全文）

### 2.1 入口 FindMatchingRecipe（:141-176）——判定流程

```
FindMatchingRecipe(terrain, ingredients[9], heatLevel, playerLevel)
1. ingredients 全空 → 返 null（:142-144）
2. ad-hoc 优先：按 index 遍历 BlocksManager.Blocks 全部方块（:146-154），
   调 block.GetAdHocCraftingRecipe(terrain, ingredients, heat, level)；
   返非 null 且 MatchRecipe(其Ingredients, 实际格) 通过 → **立即 break 采用**
3. 静态表：无 ad-hoc 命中 → 按 m_recipes 现序线性扫（:155-162），
   首个 MatchRecipe 通过者采用（短路与，后到者无关）
4. 门禁（:163-173）：命中后若 heatLevel < RequiredHeatLevel
   → 返**只带 Message 的假配方**（ResultValue=0；heatLevel≤0 用文案0，>0 用文案1 :165-167）；
   若 playerLevel < RequiredPlayerLevel 且 EnableLevelRestrictions
   → 同款假配方（按是否需热分文案2/3 :169-173）
5. 假配方也是 CraftingRecipe → 调用方必须判 ResultValue!=0 而非只判 null
```

### 2.2 MatchRecipe（:220-259）——对齐穷举

- mod 钩子 `MatchRecipe` 最先执行（:223-232）：任一 mod 声明接管（out flag=true）则**整体替换**引擎匹配。
- `actualIngredients.Length > 9` 直接 false（:233-235）。**反过来实际数组必须足 9 长**：比较循环固定走到 9（:244-251），提前撞上 `l == actualIngredients.Length` 记 flag=false——mod 代码传短数组永远匹配失败，空格要填 null 补齐到 9。
- 穷举空间：`flip ∈ {false,true}`（镜像）× `shiftX,shiftY ∈ [-4,2]`（平移），共 2×7×7=98 次变换（:237-240）。**没有旋转**：方向敏感的形状（如 L 形）只有原样和左右镜像两种可命中。
- 每次变换把配方阵重排进 9 格临时阵，再逐格 `CompareIngredients`（:244-251），全 9 格相等即 true。实际数组不足 9 时循环照样走到 9 → 见上一条的陷阱。

### 2.3 TransformRecipe（:261-282）——单次平移/镜像

- 对配方阵每格 `(k=列, j=行)`：flip 时列取 `3-k-1`（水平翻转），加 shiftX/shiftY 落点（:265-274）。
- 非空格被平移出 [0,3) 边界 → 整次变换失败（:276-278）；空格挪出界无所谓。故 1×1/2×2 配方可落在 3×3 网格任意角落，2×2 玩家网格只能容下 ≤2 宽/高的配方。

### 2.4 CompareIngredients（:284-304）——单格判等

```
required==null ⇔ actual==null（空对空 :285-291）
双侧 DecodeIngredient 拆成 craftingId + data?（:292-293）
actual 无 :data → 抛 InvalidOperationException（:294-296）
  ——所以网格编码方恒拼 "id:data"（ComponentCraftingTable.cs:140、ComponentFurnace.cs:244）
craftingId 相等且（required 无 data → 通配任意 data :298-299；否则 data 精确相等 :301）
```

- **匹配完全不看堆叠数**：格子里 1 个还是 64 个不影响判定；数量只决定"能合成几次"（§4.2）。
- **匹配胜负与排序无关**：线性扫按列表现序取首个命中，而列表序是 `Initialize` 排出来的——DisplayOrder 升序，同序按**非空配料数降序**（:37-49，`Compare(x,y)` 拿 r2 的数量比 r1 的），即"更复杂的配方排前面"。这影响配方书展示次序，也可能在两条真重叠的配方间充当优先级。
- `Initialize`（:18-57）顺序：mod XML 合并 `LoadCr`（:21-24）→ `LoadData` 递归解码（:59-83，`OnCraftingRecipeDecode` 钩子可整体接管单条）→ 遍历方块收 `GetProceduralCraftingRecipes`（:25-28）→ `CraftingRecipesManagerInitialize` 钩子（可改表+`ref sort` 关排序 :30-36）→ 排序 → `Initialized` 钩子（:50-56）。
- `DecodeElementToCraftingRecipe`（:85-139）：属性小写单字母=配料变量（:107-119），正文每行引号内为 pattern 行，`Ingredients[j + i*3]`（`horizontalLen` 缺省 3，:120-137）；data 范围限 0..0x3FFFF（:114-117）。`DecodeResult` 用**方块类名**查 `BlockNameToIndex`（:193，表在 BlocksManager.cs:96 填充），`DecodeIngredient` 用 **craftingId**（:215-217）——产物与配料是两套名字体系。

## 3 成分描述与通配（craftingId 机制）

| 机制 | 实现 | 出处 |
|---|---|---|
| craftingId 定义 | BlocksData.txt 第 15 列字符串，加载时反射灌进 `Block.CraftingId`（Block.cs:47，默认空串） | BlocksManager.cs:1037-1083（LoadBlocksData） |
| 通配"任意原木" | 5 个原木方块共用 `wood`（Oak/Birch/Spruce/Mimosa/Poplar）——多 Block 同 craftingId 即"任一均可" | BlocksData.txt（awk $15=="wood" 实测 5 行） |
| 通配"任意颜色/耐久/木种" | 配方串不写 `:data` → 任意 data 命中 | CompareIngredients :298-299 |
| 定色/定档 | 配方串写 `:data` → data 精确相等（如 `seeds:5`） | :301；XML 实例 CraftingRecipes.xml `a="seeds:5"` |
| 网格侧编码 | `$"{block.GetCraftingId(value)}:{data}"`，data 恒带上 | ComponentCraftingTable.cs:140 |
| 图标轮播 | 配料命中多个方块时按 `Time.RealTime` 取模轮换显示 | CraftingRecipeSlotWidget.cs:38-48 |
| 间接耐久参与 | 染色类动态配方用 `BlocksManager.DamageItem` 把损耗后的颜料桶当 Remains 返回——耐久在 data 里，匹配本身仍是 data 等值 | CarpetBlock.cs:129-144；ClothingBlock.cs:216-232 |

- 耐久没有独立匹配维度：工具/容器的损耗就是 data 位（`GetDamage`），静态配方不写 `:data` 时损耗品照常匹配。
- **单格没有"多选一"语法**：一格只能指一个 craftingId；要"木或石"只能拆两条配方或走 mod 钩子。

## 4 Remains 与工作台数据流

### 4.1 两种网格，一个类（ComponentCraftingTable）

| 宿主 | SlotsCount | 网格 | 出处 |
|---|---|---|---|
| 世界工作台（方块 27）实体模板 | 11 = 9 格+产物+余渣 | 3×3 | Database.xml:3394-3400（SlotsCount=11）；UI CraftingTableWidget.xml CraftingGrid 3×3 |
| 玩家自带（Player 模板成员组件） | 6 = 4 格+产物+余渣 | 2×2 | Database.xml Player 模板 CraftingTable SlotsCount=6；UI FullInventoryWidget.xml CraftingGrid 2×2（ComponentGui.cs:544-553 开包时挂） |

- `m_craftingGridSize = sqrt(SlotsCount-2)`（ComponentCraftingTable.cs:124）——类本身支持任意 N×N，2×2 与 3×3 的差异只在模板槽位数与 UI 网格尺寸，匹配代码零分支。
- 槽位约定：末两格=产物（`SlotsCount-2` :20）/余渣（`SlotsCount-1` :13）；`GetSlotCapacity` 对这两格返 0 拒收玩家塞入（:32-37）。
- 2×2 网格编码进 3×3 阵：`matched[i + j*3]`、槽位 `i + j*gridSize`（:130-133）——2×2 内容映射到 3×3 左上角，其余格 null。
- 失效驱动：`AddSlotItems`/`RemoveSlotItems` 置 `m_recipeUpdateNeeded`；从空变非空（或非空变空）再置 `m_recipeRefindNeeded`（:39-47/:49-106）；`Update` 里重算（:24-30）。refind=false 时**沿用旧配方**只刷新数量（:151-161）。

### 4.2 一次取货的数量账（RemoveSlotItems @ ResultSlotIndex :55-90）

1. `num = min(网格非空格堆叠数)`（:128-147）→ 产物槽显示 `ResultCount × num`（:166）。
2. 取 N 个先向下取整到 `ResultCount` 的倍数（:70）。
3. 若有余渣：取货量被**余渣槽剩余容量**封顶（`余容量/RemainsCount × ResultCount` :56-69）——余渣满了拿不走产物；余渣槽非空且值不同 → 禁取（:66-68）。
4. 扣料：每个匹配到的网格格 `- N/ResultCount`（按 `i%3 + gridSize*(i/3)` 映射回实际槽 :72-78）。
5. 回填：余渣槽 `+= N/ResultCount × RemainsCount`（:79-83）。

### 4.3 UI 不复用匹配器

- `CraftingRecipeWidget.UpdateWidgets`（CraftingRecipeWidget.cs:63-88）把某条配方的 `Ingredients[9]` 直接摆进 3×3 `CraftingRecipeSlotWidget`——纯展示，不做匹配；产物同理 `SetResult`。
- `CraftingRecipeSlotWidget.SetIngredient`（CraftingRecipeSlotWidget.cs:23-33）存字符串，测量时 `DecodeIngredient`+`FindBlocksByCraftingId` 解析成图标。
- 配方书只过滤不匹配：`RecipaediaRecipesScreen.cs:30` 按 `ResultValue == value` 筛 `CraftingRecipesManager.Recipes`。
- 想做"合成预览/自定义匹配 UI"，正确姿势是调用 `FindMatchingRecipe` 本尊，而不是从 Widget 里找（Widget 层没有匹配逻辑）。

### 4.4 Remains 语义汇总

- 配方级：可选字段，熔炉/工作台同一套字段与回填规则（熔炉出货 :133-137）。
- 余渣槽是**真实槽位**：可手动取出、可续堆（同值才续 :59-63），工作台销毁时随其余槽一起掉落、唯独产物槽不掉（DropAllItems 跳过 ResultSlotIndex :108-120）。
- 原版把 Remains 用作"带损耗返还容器"：染地毯/染衣后颜料桶带着新增损耗回去（CarpetBlock.cs:138-140、ClothingBlock.cs:230-232），而非单纯的空桶。

## 5 熔炉差异（ComponentFurnace.cs，本日全文）

| 维度 | 工作台 | 熔炉 |
|---|---|---|
| 配方类 | CraftingRecipe | **同一个类**；无 SmeltingRecipe——`RequiredHeatLevel>0` 即烧制配方 |
| 槽位 | 11/6 槽，末两格产物/余渣 | 5 槽（Database.xml:3404-3407）：输入 `SlotsCount-3` 个（`m_furnaceSize=2` :223）+ 燃料/产物/余渣（:62-66） |
| 匹配输入 | 9 格 3×3 阵 | 只编码前 `m_furnaceSize` 格进 `string[9]`（:236-249），其余 null——配方须 ≤2 格且靠平移贴齐左上 |
| 匹配器 | FindMatchingRecipe，heat 恒 0 | **同一个** FindMatchingRecipe（:253），heat 传实时火温 |
| 二次过滤 | 无 | 命中后要求 `RequiredHeatLevel>0`（:256-258，防烧台配方混入）、产物槽同值且容量足（:260-267）、余渣槽同值且容量足（:268-282） |
| 热量来源 | 无关 | 燃烧中用 `m_heatLevel`，熄火时预览燃料槽物品的 `GetFuelHeatLevel`（:165-175）；燃料槽 `GetSlotCapacity` 拒收非燃料（:74-82） |
| 燃料逻辑 | 无 | `UseFuel` 每次扣 1 燃料、按 `GetFuelFireDuration × FuelTimeEfficiency` 续燃（:187-205）；爆炸物当燃料直接引爆（:193-196） |
| 出货 | 取货时扣格+回填余渣（§4.2） | 进度满 1 自动：每输入格 -1、产物+ResultCount、余渣+RemainsCount（:123-142）；`SmeltSpeed=0.15/s`（:26）≈6.7s 一次 |
| 空烧/回退 | 无 | 无配方即熄（`StopFuelWhenNoRecipeIsActive` :24、:109-114）；断火进度按 `SmeltProgressReductionSpeed` 回退，默认 +∞ 清零（:31、:119-122） |
| 配方切换 | 换料重匹配 | 换料进度清零重来（:177-180） |

## 6 mod 视角：三条注册路 + 动态配方可行性

| 路线 | 窗口/入口 | 匹配行为 | 证据 |
|---|---|---|---|
| XML 数据 | mod 包内 CraftingRecipes.xml，`ModEntity.LoadCr` 合并进同一棵 XElement → `LoadData` | 静态表一员，翻译/镜像/通配全自动；`OnCraftingRecipeDecode` 钩子可单条接管或改写 | CraftingRecipesManager.cs:21-24/:59-83 |
| 代码注册 | `CraftingRecipesManagerInitialize` 钩子里往 `m_recipes`（public static List）增删改，`ref sort=false` 可关自动排序 | 同上；init 期一次性，运行期改表也即时生效（匹配每次现查表）[推测：无人缓存表快照] | :30-36/:8-9 |
| 程序化覆盖 | 重写 Block 的 `GetProceduralCraftingRecipes()`（批量静态）或 `GetAdHocCraftingRecipe()`（逐次动态） | procedural 进表；ad-hoc **优先于全表**、每次重算现调 | Block.cs:326-333；匹配序 :146-162 |

**动态/条件配方可行，且有原版三例**（均 `GetAdHocCraftingRecipe` 覆写，输入即当前网格+热量+玩家等级，输出可运行时构造）：

1. `FurnitureBlock`（:436-530）：按格子里的家具设计 data 现场生成按钮/开关变体家具，`Ingredients = (string[])ingredients.Clone()` 让自己的"配方"等于玩家摆的阵。
2. `ClothingBlock`（:189-244）：`CanBeDyed` 不满足 → 返 null（条件拒绝）；颜色混合后连同损耗颜料桶 Remains 一起现造。
3. `CarpetBlock`（:103-150）：混色无变化（颜色相同）→ 返 null；产物/余渣 data 全运行时算。

注意点：ad-hoc 挂在 Block 上，返回后仍要过一道 `MatchRecipe`（:148-153）——惯例是把实际 ingredients 原样塞进返回配方的 Ingredients（如上三例）。全局改匹配规则用 `MatchRecipe`/`DecodeIngredient`/`DecodeResult` 三个 mod 钩子（:223-232/:203-209/:181-187），接管后引擎判等完全旁路。
